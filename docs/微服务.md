### 什么是微服务

- 微服务是一种架构风格
- 一个应用拆分为一组小型服务
- 每个服务运行在自己的进程内，也就是可独立部署和升级
- 服务之间使用轻量级HTTP交互
- 服务围绕业务功能拆分
- 可以由全自动部署机制独立部署
- 去中心化，服务自治。服务可以使用不同的语言、不同的存储技术

## 熔断降级

### 1.为什么需要熔断降级？

分布式系统中，服务间依赖关系复杂（如 A 依赖 B，B 依赖 C），一旦某个环节（如 C）故障，若 A 仍持续向 B 发送请求，B 又持续调用 C，会导致：

1. **资源耗尽**：B 的线程、连接池被大量 “等待 C 响应” 的请求占满，无法处理其他正常请求；
2. **级联故障**：B 不可用后，A 的请求也会堆积，最终导致整个链路崩溃；
3. **用户体验差**：用户请求长时间等待后返回 “500 错误”，而非明确的友好提示。

熔断降级正是为解决这些问题而生 —— 通过 “主动干预”，让系统在故障时 “优雅降级”，而非被动崩溃。

### 2.熔断

熔断的核心逻辑源于日常生活中的 “电路断路器”：当电路过载或短路时，保险丝会主动断开，避免电路烧毁；故障修复后，电路再尝试恢复通路。

在系统中，熔断针对的是 “对外部依赖服务的调用”（如服务 A 调用服务 B），通过**监控调用失败率**，动态调整 “是否允许发起调用”，从而避免无效请求浪费资源。

#### 1.熔断的三个核心状态

| 状态（State）             | 核心逻辑                                                     | 适用场景                                       |
| ------------------------- | ------------------------------------------------------------ | ---------------------------------------------- |
| **闭合状态（Closed）**    | 正常允许调用依赖服务；同时监控调用的失败率（如超时、5xx 错误）。 | 依赖服务正常可用时。                           |
| **打开状态（Open）**      | 当失败率超过预设阈值（如 50%），熔断触发，**直接拒绝调用**，不向依赖服务发送请求；同时启动 “超时计时器”（如 5 秒）。 | 依赖服务已故障，持续调用只会浪费资源时。       |
| **半开状态（Half-Open）** | 超时计时器结束后，进入半开状态：允许 “少量试探性请求” 调用依赖服务。 - 若试探请求成功：说明依赖服务已恢复，切回 “闭合状态”； - 若试探请求仍失败：说明服务未恢复，切回 “打开状态”，重新计时。 | 故障后尝试恢复，避免 “过早恢复” 导致再次故障。 |

#### 2.熔断的典型应用场景

- **微服务间调用**：如订单服务调用支付服务，若支付服务超时 / 报错率过高，订单服务触发熔断，不再调用支付服务，直接返回 “支付服务暂时不可用，请稍后重试”。
- **API 网关层**：网关调用后端服务时，若某服务故障，网关触发熔断，拦截所有指向该服务的请求，避免请求穿透到故障服务。
- **数据库访问**：若数据库连接超时 / 查询失败率高，应用层触发熔断，不再执行数据库操作，改用缓存数据或返回默认值。

### 3.降级

降级的核心逻辑是：当系统**整体资源不足**（如 CPU / 内存使用率过高、流量突增）或**非核心功能故障**时，主动 “关闭非核心功能” 或 “降低非核心功能的体验”，将资源优先分配给核心功能，确保核心业务正常运行。

降级的本质是 “资源调度策略”—— 通过牺牲非核心功能，换取核心功能的稳定性。

#### 1. 降级的三种常见类型

| 降级类型                     | 触发条件                                                     | 执行逻辑                                           | 示例                                                         |
| ---------------------------- | ------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------------ |
| **主动降级（人工触发）**     | 预知系统压力（如大促、秒杀活动前），或发现潜在风险时。       | 人工关闭非核心功能，提前释放资源。                 | 电商大促前，关闭 “商品评价修改”“历史订单导出” 等非核心功能，优先保障 “下单”“支付”。 |
| **自动降级（系统触发）**     | 系统监控到资源过载（如 CPU>90%、内存 > 85%），或流量超过阈值。 | 系统自动触发降级规则，关闭 / 弱化非核心功能。      | 视频 APP 在晚高峰流量突增时，自动将 “4K 画质” 降级为 “1080P”，减少带宽消耗。 |
| **故障降级（依赖故障触发）** | 非核心功能依赖的服务 / 资源故障（如缓存失效、第三方 API 不可用）。 | 不再等待故障依赖的响应，直接返回默认值或缓存数据。 | 电商商品详情页的 “猜你喜欢” 模块依赖推荐服务，若推荐服务故障，直接不显示该模块，或显示固定的 “热门商品” 列表。 |

#### 2.降级的核心原则

降级的前提是明确 “核心功能” 和 “非核心功能” 的边界，绝对不能牺牲核心业务。例如：

- 银行系统：核心功能是 “转账”“取款”，非核心功能是 “理财推荐”“账单分析”；
- 外卖系统：核心功能是 “下单”“接单”“配送跟踪”，非核心功能是 “用户等级积分查询”“历史订单统计”。

### 4.熔断 vs 降级

| 对比维度     | 熔断（Circuit Breaking）                            | 降级（Degradation）                                   |
| ------------ | --------------------------------------------------- | ----------------------------------------------------- |
| **核心目标** | 保护 “调用方”，避免无效请求浪费资源（防止故障扩散） | 保护 “整体系统”，优先保障核心功能（资源调度）         |
| **触发条件** | 依赖服务的 “调用失败率 / 超时率” 超过阈值           | 系统资源过载、流量突增，或非核心功能故障              |
| **作用对象** | 针对 “对外部依赖的调用”（如 A 调用 B）              | 针对 “系统内部的功能模块”（如核心功能 vs 非核心功能） |
| **执行逻辑** | 断连 / 恢复调用（状态机切换）                       | 关闭 / 弱化功能（资源重新分配）                       |
| **典型场景** | 依赖服务故障时，停止调用该服务                      | 系统过载时，关闭非核心功能                            |

### 5.熔断降级的实际落地工具

- **微服务框架**：Spring Cloud（Resilience4j、Sentinel）、Dubbo（自带熔断降级能力）；
- **API 网关**：Kong、Nginx（通过 Lua 脚本实现）、Spring Cloud Gateway；
- **中间件**：Redis（缓存降级，如缓存穿透时返回默认值）、MQ（流量削峰，间接辅助降级）。

**总结**

熔断和降级是分布式系统的 “安全阀”：

- **熔断**是 “点对点的保护”—— 当依赖服务故障时，切断调用链路，避免自身被拖垮；
- **降级**是 “全局的取舍”—— 当系统资源不足时，牺牲非核心功能，保障核心业务。

### 6.具体方案

Dubbo 可与 Sentinel 无缝集成，通过 Sentinel 控制台或代码配置熔断规则，监控 Dubbo 服务的调用指标（错误率、响应时间等）。

1. 当 Dubbo 服务调用的异常率超过阈值（如 50%），Sentinel 触发熔断，拦截后续调用。
2. 熔断期间，调用方会执行预设的降级逻辑（如返回 mock 数据）。
3. 熔断时长结束后，Sentinel 允许少量试探性调用，若成功则恢复正常，否则继续熔断。

 Gateway 本身不直接提供熔断降级功能，而是通过集成 **Resilience4j** 或 **Sentinel** 等组件实现。

当 Redis 故障导致异常率过高时，Sentinel 触发熔断，直接执行降级逻辑，不再调用 Redis，避免资源浪费。

## 高并发系统设计

**问题**：一个中台项目，有 A、 B、 C 三个系统，目前所处的是 B 系统。然后有前台有大量的请求转发进来， B 系统主要负责查询，与数据库交互。如果大量的请求B系统承受不了，然后如何从从前到后的去进行限制。有什么方法来去限流，或者是减少服务器压力？

应对大量请求，核心思路是 **“分流、削峰、缓存、降级”**。你不能期望单靠某一层或某一个技术就能解决所有问题，必须构建一个多层次的防护体系。

#### 整体架构应遵循以下优先级

1. **最外层拦截**：在流量到达应用服务器前，尽可能阻挡无效或过量的流量。
2. **应用层削峰**：在应用服务器内部，控制并发执行的请求数量，避免资源耗尽。
3. **数据层保护**：优化数据库查询，并通过缓存减轻其直接压力。
4. **优雅降级**：当压力实在超出极限时，保证核心功能可用，牺牲非核心功能。

### 分层限流与减压方案详解

#### 1. 前台 / 接入层限流 (边缘防护)

这是第一道防线，目标是在流量进入你的核心服务前就进行控制。

**CDN (内容分发网络)**

- **作用**：将静态资源（如图片、JS、CSS）缓存到离用户最近的节点。这不仅加速了用户访问，更重要的是**直接减少了对源站（你的服务器）的请求量**。
- **操作**：将所有静态资源上云，通过 CDN 进行分发。

**API Gateway**

- **作用**：这是所有请求进入你系统的 “大门”。在这里进行限流，可以保护后面所有的应用服务器。
- **方法**：
  - **IP 限流**：限制单个 IP 在单位时间内的最大请求数。防止来自单个恶意 IP 的攻击。
  - **Token / 用户限流**：基于用户 ID 或 API Token 进行限流，比 IP 更精准，能防止单个用户的滥用。
  - **关键技术**：通常使用 Nginx、HAProxy 或云服务商提供的 API Gateway来实现。它们性能极高，能轻松应对百万级并发。

#### 2. 本台服务器限流 (应用层防护)

如果流量穿透了第一道防线，就需要在应用服务器（B 系统）自身进行控制。

**速率限制 (Rate Limiting)**

- **作用**：在代码层面，精确控制某个接口或服务的访问速率。
- **关键技术**：
  - **令牌桶算法 (Token Bucket)**：想象一个装令牌的桶，系统按固定速率往桶里放令牌。每个请求来临时，必须拿到一个令牌才能执行。这能平滑突发流量。
  - **漏桶算法 (Leaky Bucket)**：想象一个漏水的桶，请求像水一样注入，桶以恒定速率漏水（处理请求）。如果水注入过快，桶会溢出（请求被丢弃）。这能严格控制输出速率。
  - **实现**：可以使用 Guava RateLimiter (单机) 或 Redis + Lua 脚本 (分布式) 来实现。

#### 3. 数据库减压 (数据层防护)

B 系统的核心是查询数据库，所以保护好数据库是重中之重。

**Redis缓存**

将高频访问、变化不频繁的数据存放在缓存中，避免每次都去查询数据库。

**数据库查询优化**

**作用**：从根源上减少数据库的查询时间和资源消耗。

**操作**：

- **SQL 审查与优化**：使用 `EXPLAIN` 分析 SQL 执行计划，避免 `SELECT *`，确保 `WHERE` 和 `JOIN` 的字段都建立了索引。
- **索引优化**：建立合适的索引，但也要避免过度索引。
- **读写分离**：将读操作和写操作分发到不同的数据库服务器。主库负责写，从库负责读，能极大提升查询吞吐量。
